> Historical observations from 27 October. The production fixes and deployed retest are documented in [the updated rollout report](staging-fixes-2026-10-27.md), including successful hosted invoice TESZT-2026-6 on 28 October. The failures below describe the pre-release state.

**Result: not ready for live use.** The current backend source completed a real
test-account invoice from approved time through stored PDF and invoiced work.

critical tenant-isolation and signup-authorization defects. A newly discovered
invoice retry-loop defect was fixed, tested and deployed with explicit approval.

## Recovery and the deployed fix

| Injected condition | Actual staging database behavior |
| --- | --- |
| Explicit provider rejection | 422, failed ledger row, work editable again |
| Lost/unknown provider response | 502, uncertain ledger row, work remained reserved |
| Repeat uncertain request | 409 before another provider callback; callback count zero |
| Confirmed not issued | Reconciled to failed and released the reservation |
| Local finalization failure after simulated provider success | 502, uncertain ledger row, work remained reserved |
| Confirmed issued | Reconciled to issued and changed captured work to invoiced |

The first reserved-entry edit checks timed out twice. Hosted logs identified
**PostgREST 14.5**, SQLSTATE **40001**, the invoice protection trigger and repeated
transactions. Supabase documents this exact retry-loop behavior in its
[40001 troubleshooting guide](https://supabase.com/kb/troubleshooting/high-cpu-and-infinite-transaction-retries-when-using-custom-error-codes-in-rpc-functions).
One confirmed looping test backend was terminated; the other was no longer
running when checked.

Migration
[`20261027091353_avoid_retryable_invoice_business_conflicts.sql`](../supabase/migrations/20261027091353_avoid_retryable_invoice_business_conflicts.sql)
changes the business-conflict code to `PT409` in five existing invoice functions.
It preserves their signatures, permissions and reservation rules. After user
approval, it was applied to hosted ChronoSync and migration history was aligned
to version `20261027091353`. Read-back verified all five functions use `PT409`
and none retain `40001`. Reserved edits then returned **409 immediately**, and
all 14 staging recovery assertions passed.

The Python reservation, finalization and attachment handlers now recognize
`PT409` as a conflict while retaining compatibility with the old code. Those
Python changes are local and still need backend deployment.

The SQL fixture originally lacked authenticated read grants on clients/projects.
Some edit tests therefore failed before reaching the reservation guard. The
fixture now matches those hosted lookup grants. A positive edit control and an
exact SQLSTATE assertion verify the actual invoice protection behavior.

## Remaining release blockers

| Priority | Finding | Required action |
| --- | --- | --- |
| Critical | `profiles` policy `all_temp` permits all authenticated operations with unconditional predicates. The staging admin read 13 profiles outside its company. | Replace broad policies with tenant-scoped policies and protect role/company/active-state changes at the database boundary. Test with both ordinary users and company admins. |
| Critical | The company ALL policy accepts any company admin without a company-ID predicate. The staging admin could read all three companies. | Scope company admins to their own company; retain explicit super-admin handling. Verify read and mutation boundaries. |
| Critical | `handle_new_user` assigns company and role from user-editable signup metadata. | Move privileged provisioning/invitations behind trusted admin authorization. Do not trust requested signup roles or tenant membership. |
| Critical | `leave_requests` has RLS disabled and anonymous table grants. A read-only check under the anonymous role counted all 14 existing requests. | Enable and test appropriate RLS and grants before release. No existing leave contents were needed for this proof. |
| High | Deployed provider previews still return 502. The identical saved profile returns 200 and a valid PDF through current source, including after the conflict migration. | Deploy the tested backend/frontend and rerun the fully hosted review/preview/issue flow. The unshipped compressed-response fix is a likely cause, but the deployed revision/logs were not available to establish the exact cause. |
| Medium | Issued reconciliation finalizes with `pdf=None`. The simulated recovered invoice has `pdf_available=false`. | Add verified provider PDF retrieval/storage or make the manual PDF recovery path explicit. |
| Medium | In-app user creation uses public signup and a hardcoded temporary password. The synthetic worker required email confirmation. | Implement trusted invitations and a usable credential setup flow; verify actual email delivery and account activation. |

The security advisor still reports the disabled leave RLS, mutable search paths,
publicly executable definer functions, and disabled leaked-password protection.
Advisor warnings about definer functions require individual review; they do not
by themselves prove an exploitable function. Supabase's
[RLS remediation](https://supabase.com/docs/guides/database/database-linter?lint=0013_rls_disabled_in_public)
and [password-security guidance](https://supabase.com/docs/guides/auth/password-security#password-strength-and-leaked-password-protection)
are the relevant primary references.

## Final state and limits

The retained synthetic company contains **10 clients, 4 projects, 2 users and
4 entries**. Its four ledger rows comprise one actual provider invoice, one
explicitly simulated issued recovery, and two failed simulations. There are
**zero issuing or uncertain attempts**.

The staging company was returned to preview mode and deactivated. Both temporary
logins were banned, the worker profile was deactivated, and the admin's refresh
sessions were revoked. A new admin sign-in was verified to fail with
`user_banned`. The sole-admin database guard keeps that profile's `is_active`
flag true; the Auth ban and company deactivation prevent ordinary sign-in/use.
Any already-issued access JWT remains valid until expiry, as with Supabase
sign-out generally. Temporary session/password files were removed and the local
servers stopped. Test data and PDFs remain for review.

The deployed backend's provider creation path did not receive a request in this
run. Its working stored-PDF/history APIs do not establish hosted provider
issuance readiness. Railway CLI authentication is expired, so no backend deploy
was performed. The frontend also still shows the older tax-field wording.

No invoice-email delivery, NAV reporting, production invoices, online payments,
delivered signup/recovery emails, complete leave-approval flow, logo-upload flow,
or exhaustive mobile/browser matrix was certified. Timer and several utility
paths are covered by the frontend regression suite, rather than a new hosted
browser run. The successful source test and regression suite therefore do not
support a claim that the deployed application is flawless.
